# Stage 19: persistent storage -- a second disk, mounts, `/etc/fstab` -- `r19_mounts` (plan)

`ROADMAP.md` carries the summary of this stage; this file is the plan: the decisions, and the steps in the order they are built and committed. It is updated as each step lands (an "As built" note per step, as `Stage17.md` and `Stage18.md` do). ## Decisions (settled)
- **Two labels, no `/home/root`.** The system image is labelled `SYSTEM` and is `/`; the persistent disk is labelled `HOME` and is mounted at `/root`, the directory Stage 17 already made the shell's `$HOME` (there is no login or user system, so `/home/<user>` would only add a level; `/home/root` is not the Linux convention either -- root's home is `/root`). Labels rather than `ROOT`/`DATA`, so that "ROOT on `/`, DATA on `/root`" is never read backwards.
- **The kernel mounts the root; the shell mounts the rest.** Linux's `root=` versus `mount -a`. The root is chosen before any file can be read: the volume labelled `SYSTEM`, else the first device, so every earlier image (label `R12SH`) still boots. A `root=LABEL=` on a kernel command line (QEMU `-append` becomes the DTB's `/chosen/bootargs`) is possible later and not needed while the label rule works.
- **`/etc/fstab`:** `<source> <mount point> <type> <options>`, whitespace-separated, `#` comments, `LABEL=`/`UUID=` sources (UUID is the FAT volume ID, `XXXX-XXXX`), type `vfat` or `fat`, options only `defaults` (= `auto,fail`), `auto`/`noauto` and `fail`/`nofail` (`ro` and anything else refused with a note), `dump`/`pass` ignored. Mounted in file order. The image ships one line: `LABEL=HOME /root vfat defaults`. A `/` line is accepted but informational (checked against the volume that is the root; mismatch is a note); none is shipped.
- **Every problem is a serial-log note, never fatal:** missing file, bad line, no matching device, duplicate label (first wins), mount point not a directory. With no home disk, `/root` is an empty directory on the system volume and the shell starts there.
- **Identification by what is on the disk:** FAT volume label and volume ID from the boot sector (via `hadris`: `volume_label()`, `volume_id()`; `mlabel` changes both the boot sector and the root-directory label). Not by MMIO slot (QEMU's order is not the command-line order), not by the virtio serial, no partition table so no `PARTUUID`. All images so far have volume ID `0000-0000`; `just home-disk` stamps a distinct one.
- **Path resolution:** longest matching mount-point prefix on the normalized absolute path; the remainder goes to that volume. A mount point must exist as a directory on the volume beneath it; what it hid stays hidden while mounted.
- **`lsblk`, `mount`, `umount` are programs over syscalls, not builtins** (decided after listing what the shell has: `cd`, `source`/`.`, `sh`, `export`, `unset` are builtins because they change the shell's own state; these change none). One syscall per Step where needed: `blkinfo` in Step 1, `mount`/`umount` in Step 5.
- **Cross-volume `rename` is `EXDEV`;** `mv` (in the new tier, extending Stage 18's) falls back to a copy and a removal, for files **and directory trees**. The order is POSIX's, safer than GNU's remove-as-you-go: nothing of the source is touched until the whole copy exists and each file's size checked. The copy is made under a hidden temporary name in the destination directory -- **`.mv-partial`, or `.mv-partial.1`, `.2`, ... for the first that is free** (fixed length whatever the source is called, like the shell's `/tmp/.pipeN`; hidden by `ls`, found by `ls -a`) -- and renamed into place when complete, so a half-copied tree never appears under the real name; on failure it is removed and the source is whole; after a crash it is a dot-file to `rm -r`. If removing the source fails part-way, the destination is complete and `mv` says which entry it could not remove. Replacing an existing file goes through the same temporary name and the kernel's replacing `rename`, so the old file is never truncated or deleted first (Stage 18's `mv` unlinked the target before renaming: across volumes that lost it when the rename then failed with `EXDEV`).
- **`rename` replaces (4a).** As POSIX's: a file replaces a file, a directory replaces an *empty* directory (`ENOTEMPTY` otherwise), a file onto a directory is `EISDIR` and a directory onto a file `ENOTDIR`, a directory into its own subtree `EINVAL` (checked before anything is removed), the same path is a no-op. On FAT it is not atomic: the old destination is removed and then the source renamed, so a crash between them loses only the file that was to be replaced. `mv`'s own rules (`mv a dir` moves *into* `dir`, `-n`, the trailing-slash rules) stay in the program.
- **`utimensat` (4b).** Linux's number (88) and its two-`timespec` array (access, modify) with `UTIME_NOW` and `UTIME_OMIT`, shape simplified like the other path syscalls (no dirfd, no flags: `path, path_len, times`). FAT stores a modify time to 2 seconds and an access *date*; times outside 1980-2107 are `EINVAL`, nanoseconds are dropped, and the creation time is not settable (nor is it on Linux). It goes through `hadris`' `FatVolume::set_times`, which works on files and directories from a path. `touch` (in `progs_r19`, with the time-zone database `date` already links) gains **`-d STRING`** (`@SECONDS`, `YYYY-MM-DD`, `YYYY-MM-DD HH:MM[:SS]`, `T` for the space), **`-t [[CC]YY]MMDDhhmm[.ss]`** and **`-r FILE`**, in the local zone (`$TZ`) like `date`; **`cp -p`** keeps modify time and the read-only/exec bits, for files and (with `-r`) directories. Not `touch -a`/`-m` (an access date nothing shows).
- **Host side:** `just run` rebuilds the system image every time and attaches `home.img`, which is created once and never rebuilt; the host must not touch it while QEMU runs.
- **Documentation stays stage-agnostic** (`<stage>` for what changes per stage; name the stage for a change attributable to one): new rows say "From Stage 19".

## The mount rules (settled after Step 2)
Written out in full, with the Linux comparison, in `rust/docs/filesystem.md` ("Mounts"). In short: a path goes to the mount with the **longest point** matching on a whole component; a mount goes on an existing directory of the volume its path resolves to, **including a subdirectory of a mounted volume**; **a point holds one mount** (`EBUSY`), **a mount cannot cover another mount** (`EBUSY`), **a volume is mounted once** (`EBUSY`); `umount` takes the exact point, innermost first, and is `EBUSY` for the root, a volume with an open file or a working directory inside it, or one with a mount inside it; a mount point cannot be removed or renamed (`EBUSY`); a rename between volumes is `EXDEV`. These are deliberately **stricter than Linux** in three places (stacking on a point, mounting on a parent of a mount, mounting one device twice); the table stays a list of unique points, and nothing planned needs more.

## Not doing
`touch -a`/`-m`, `mv -i`/`-u`/`-b`/`-t`/`-T`, preserving anything but times and the two attribute bits (FAT has no owners, links or extended attributes). `mount` reading `/etc/fstab` (Linux's one-operand `mount /mnt` and `mount LABEL=HOME`, which fill the other operand in from the file, and `mount -a`): `mount` stays explicit, taking both operands, so a `noauto` line is only syntax-checked -- a candidate for later, by sharing `shell/fstab.rs` with `progs_r19`. Stacked mounts on one point, mounting over a parent of an existing mount, and mounting one device at more than one point (Linux allows all three; see above). Other filesystem types, hot-plug, `/dev`, read-only mounts and further options, bind mounts, `root=` on a command line, moving a directory across volumes, naming a disk by its virtio serial.

## Step 1 -- every block device, identified by its boot sector
Nothing user-visible changes except the serial log and which disk is the root; the second disk is *found and named*, never read as a filesystem. (This moves "root = the volume labelled `SYSTEM`, else the first device" here from Step 2: without it, a second disk in a lower virtio-mmio slot than the system image would be taken for the root, so the step could not be tested with a second disk attached.)

- **Driver (`drivers/virtio/blk.rs`, `drivers/virtio/mod.rs`).** `Blk::find` (first device) becomes `Blk::find_all`, returning every virtio-blk device with its SPI, in device-tree order, up to a constant `MAX_BLK` (extra ones ignored, with a serial note). `find_mmio_transport` stays as the per-slot helper the GPU and keyboard use; the block search walks the slots itself.
- **Globals (`platform/globals.rs`, `main.rs`).** `BLK: Option<Blk>` / `BLK_SPI` become arrays of `MAX_BLK`; every found SPI is enabled, and `irq_handler` acknowledges whichever device's line fired (a short loop). The populate-before-enable ordering that `main.rs` documents holds per device.
- **`BlkIo` (`fs/blkio.rs`).** Gains a device index (`BlkIo::new(dev)`); its `Read`/`Write`/`Seek` go to `BLK[dev]`. Still one `VOL` and one filesystem: only the root is opened.
- **Probe (new `fs/bootsector.rs`).** A pure, host-tested parser (`no_std`, pulled into `hosttests` like `environment.rs`) turning sector 0 into `{label, volume_id}` or "not FAT": `0x55AA` signature, sane bytes-per-sector, the extended-boot-signature byte (`0x29`), FAT32 told from FAT12/16 by `FATSz16 == 0` and `RootEntCnt == 0`, and so the label (11 bytes, trailing spaces trimmed; `NO NAME` counts as no label, as `blkid` does) and volume ID at their offsets. Own parser rather than opening a `hadris` `FatVolume` per device: a probe must not need a valid filesystem, and a `FatVolume` would also keep a second `BlkIo` alive for nothing. After `DAIF` is cleared (the read is interrupt-driven) each device's sector 0 is read once into a small table `(index, capacity, label, volume_id)`.
- **Root choice (`main.rs`).** The volume labelled `SYSTEM` (the first, if several), else device 0; `BlkIo::new(root)` then mounts as today. Serial log, before `FAT filesystem mounted.`:
  ```
  Block devices: 2
    0: 16 MiB  SYSTEM  1A2B-3C4D  (root)
    1:  1 MiB  HOME    5E6F-7A8B
  ```
  and for a skipped device `1: 1 MiB  not a FAT volume -- ignored`. With one unlabelled device (every image before Stage 19's Step 6) the line says `(root, no SYSTEM volume: using the first device)`.
- **Syscall and program.** `blkinfo(index, *mut BlkInfo) -> 0 | -ENODEV` past the last device (additive to `abi`, wrapper in `userlib`, a row in `docs/syscalls.md`); `BlkInfo` is a fixed `#[repr(C)]` struct: capacity in bytes, `flags` (bit 0: FAT volume, bit 1: is the root), 11-byte label plus length, volume ID. New tier `user/progs_r19` (copy of `progs_r18`'s crate scaffolding) with `lsblk`: `NAME SIZE LABEL UUID MOUNTPOINT`, names `vda`, `vdb`, ... by device order, sizes in the `ls -h` style (`16M`), a non-FAT device shown with empty label/UUID, MOUNTPOINT `/` for the root and empty otherwise until Step 2.
- **Tests (new group `disks`, then more as needed).** The harness learns extra images: a module attribute (`EXTRA_DISKS`, in the manner of `ENVIRONMENT`) making each extra image from a small description -- label and volume ID for a FAT one made by `mkfs.fat -n -i`, or "blank" / "not FAT" -- and attaching it *before* or *after* the system image on the QEMU command line (a second attribute), since which one gets the lower slot is the very thing that must not matter. Cases:
  - system + `HOME` attached after, then again attached before: the serial log and `lsblk` list both volumes with the right label and ID, the `SYSTEM` one is the root (`/`), and both boots reach the same prompt with the same `ls /`;
  - a blank disk and a non-FAT (random bytes) disk: noted, ignored, boot unaffected; two `HOME` volumes: both listed (the duplicate matters only when mounting, Step 3);
  - the system image labelled `SYSTEM` is chosen even when the *other* disk is in slot 0;
  - `verify_disk` checks the extra image is **byte-identical** afterwards (nothing wrote to it) and the system image is `fsck.fat -n` clean.
  The existing groups (one disk) boot the image `just disk` builds, now labelled `SYSTEM`; `disks_odd` relabels it `R12SH` to stand for every image before Stage 19.
- **Docs.** `docs/` kernel/filesystem pages: one paragraph on multiple devices and probing (stage-agnostic wording, "From Stage 19"), the `tests.md` row.
- **Not here:** opening a second `FatVolume`, mount table, paths, `fstab`, the guest reading anything from the extra disk. `just run` still attaches one disk.

Open point for the step: the virtio-mmio slot order QEMU produces for two `-device virtio-blk-device` lines is checked empirically first (the plan does not assume it); `MAX_BLK` = 4 unless that shows a reason.

**As built (Step 1).**
- **Driver and IRQ.** `Blk::find_all` (over a new `mmio_transports` iterator that `find_mmio_transport` now uses too) fills `BLK`/`BLK_SPI` arrays of `MAX_BLK` = 4 and `BLK_COUNT`; `blk::get(dev)` reaches one; a device past the fourth is left alone with a serial note. `irq_handler` finds which line fired with a short loop. QEMU's slot order was checked first, as planned: **it is the reverse of the command line** (the device listed last is device 0), so the tests attach extra disks both ways.
- **`fs/bootsector.rs`** (pure; 11 host tests): `parse` (FAT12/16 and FAT32 layouts, signature byte `0x29`, or `0x28` for an ID and no label; anything else is not FAT), `label_is` (ASCII case-insensitive, an empty name matches nothing), `VolumeId`'s `XXXX-XXXX` display, and `pick_root`: the first `SYSTEM` volume, else the first FAT volume (not merely device 0: a blank device 0 must not become the root).
- **`fs/devices.rs`:** `probe` reads sector 0 of each device after IRQs are unmasked, logs the table (`Block devices: N`, one line each, `(root)` or the reason it is the root without the label) and stores it; `blkinfo(index)` reads it. `BlkIo::new(dev)` takes the device index; still one `VOL`.
- **Syscall 1000, `blkinfo(index, out)`** (not a Linux number; `abi::blk` holds the 32-byte record with `encode`/`decode` and its own tests; `ENODEV` added to `abi::errno`, `userlib::blkinfo`). **`lsblk [-b]`** in the new tier `user/progs_r19` (`NAME SIZE LABEL UUID MOUNTPOINT`; `table.rs` holds the column layout and `vda`, `vdb`, ... names, 5 host tests); `MOUNTPOINT` is `/` for the root, empty otherwise until Step 2.
- **Harness:** `EXTRA_DISKS` (FAT with label/ID, `blank`, `noise`; `before` picks the command-line side), `SYSTEM_LABEL`/`SYSTEM_ID` (`mlabel`), `Context.extra_imgs`/`extra_hashes`, `lsblk_table`. Four groups: `disks` (extra after the system image), `disks_first` (before), `disks_odd` (blank + noise disks, system image still `R12SH`: the root is the first FAT volume although it is device 2), `disks_many` (four extras, the fifth device ignored, duplicate labels told apart by ID); each checks the extra disks are byte-identical afterwards.
- **`home.img` moved to the repository root** (after Step 3): one gitignored file shared by every stage from 19 on, found in each stage's justfile with `` git rev-parse --show-toplevel `` (`HOME_IMG`); `home-disk`, `home-reset` and `run` all use it, so a later stage's `just run` attaches the same disk with the same contents. The seed folder stays in the stage (each stage is self-contained), used only when the file is first made.
- **Host side, folded in from Step 6** (so the second disk is there to see in `just run`, still unmountable): `just disk` now labels the system image `SYSTEM` (volume serial still fixed, `0000-0000`). **`just home-disk`** creates `home.img` (32 MiB FAT16, label `HOME`, a random volume ID, gitignored) with `folder_to_img.sh` **only if it is missing** and says so when it is not; **`just home-reset`** deletes and recreates it; `just run` depends on `home-disk`, attaches `home.img` and `disk.img`, listing `home.img` first so the system disk is `vda` (QEMU numbers against the command line). The seed folder is **`disk-home-seed/`** -- named so because it is only the starting content of a new `home.img`, never kept in step with it -- and holds just a `README.txt` for now: `.profile` and `utf8-demo.txt` move there in Step 3, when `/root` becomes the mount (moving them now would leave the interactive shell with no profile, the disk being unmountable). Checked by booting `just run`'s exact QEMU line headless: `0: 64 MiB SYSTEM 0000-0000 (root)`, `1: 32 MiB HOME <id>`.
- `just test`: **1513 checks**, 279 host tests in the kernel crate plus 20 in `abi`, `just lint` and `just check-docs` (36 programs, 18 syscalls) clean. Docs: `syscalls.md`, `progs.md`, `filesystem.md`, `virtio.md`, `tests.md`.

## Step 2 -- mounting by hand
- **Mount table (pure, `fs/mounttable.rs`, 11 host tests).** `(mount point, device)` entries, the root first; `resolve(path)` gives the device and the rest of the path within it (longest match on a whole component: `/root` covers `/root/a`, not `/rootbeer`); `add` refuses a used point or an already-mounted device, `remove` refuses the root and a mount with another inside it; `is_mount_point`, `point_of`. The same file holds `Source` (`LABEL=name` / `UUID=XXXX-XXXX`, parsed like `fstab`, matched against the boot-sector identities, first device wins) so Step 3's parser reuses it.
- **Kernel glue (`fs/mounts.rs`).** One open `FatVolume` per device (`VOLS`; the `VOL` static is gone) plus the table; `install_root` at boot, `mount(source, target)` and `umount(target)`. `mount`: `EINVAL` (bad source, or `hadris` cannot open it), `ENODEV`, `EBUSY` (device already mounted, or the point is one), `ENAMETOOLONG` (over 256 bytes, what `blkinfo` can report), and `check_directory`'s `ENOENT`/`ENOTDIR`. `umount`: `EINVAL` if not a mount point; `EBUSY` for the root, a mount with another inside it, a working directory of *any* shell frame inside it (`FrameStack::cwds`), or an open file on the device (`files::open_on`, counted per device: `OpenFile` remembers its device).
- **`files.rs`** resolves every path through the table first (`locate`); `lookup` returns a `Located` (the entry and its device, dereferencing to the entry, with `read_all`), so the launcher, `source` and the profile read from the right volume; `fs::read_path` (the start-up's reader) now goes through the table too, so `/etc` can itself be a mount. `unlink` and `rename` of a mount point are `EBUSY`; **`rename` across two volumes is `EXDEV`**, checked before anything changes.
- **ABI (additive).** `SYS_MOUNT` = 40 and `SYS_UMOUNT2` = 39 (Linux's numbers, simplified shapes: no type, flags or data), `EBUSY`, `EXDEV`; `blkinfo`'s record grew to 288 bytes to carry the mount point (256 bytes, `abi::blk::BLK_MOUNT_MAX`). `userlib::{mount, umount}`.
- **Programs (`progs_r19`).** `mount [SOURCE TARGET]` (no operands: `LABEL=HOME on /mnt type vfat` per mounted device, `UUID=` when the label is missing or shared), `umount TARGET`, and `lsblk`'s `MOUNTPOINT` column now comes from `blkinfo`.
- **Tests (group `mounts`, +115 checks; 1628 in all).** By hand: mount by label and by UUID (two volumes share `HOME`: the first by device order is taken, the ID chooses), hiding and uncovering, `..` in and out of a mount, relative paths, `find /` across it, files written, appended, copied (`cp -r`), moved, removed and run on a mounted volume, a nested mount, `EXDEV` for a file and a directory, the mount-point rules, every `mount`/`umount` error, and from the host afterwards each extra image holds what was written through it and passes `fsck.fat`.
- **Mounting over and inside mounts.** A point holds one mount (`EBUSY`, whatever the device -- Linux would stack a second one, this refuses); a directory *inside* a mounted volume can be mounted on (it must exist there, `ENOENT` otherwise); and a mount **cannot cover another mount** (mounting on `/p` while `/p/q` is a mount point is `EBUSY`): with the longest-prefix rule the inner mount would otherwise have stayed reachable through a directory the new volume does not show. Found when asked what mounting on a mounted directory or its parent does.
- **Found while testing:** `rm -r /mnt` on a mounted volume removes the volume's contents and then fails on the mount point (`Device or resource busy`), as GNU `rm` does -- so the test uses `rm -d` for the refusal. Not covered by a QEMU test: `umount` refusing for an *open file* (a program cannot hold one open while a second command runs, and the code is the `files::open_on` check); it is one line of the same `EBUSY` path the working-directory case exercises.
- **Docs.** `syscalls.md` (rows 40 and 39, the `blkinfo` layout, `EBUSY`/`EXDEV`/`ENODEV`, `rename`/`unlink`), `progs.md` (`mount`, `umount`, `lsblk`, `mv`'s cross-volume message), `filesystem.md` ("Mounts"), `tests.md`.

- **No `vdX` names (decided after Step 2 was built).** `lsblk` and `mount` had printed Linux-style names (`vda`, `vdb`, ...) that nothing could use: there is no `/dev`, and no stage in the roadmap gives a program raw access to a disk (no `dd`, `mkfs`, `fsck`; they are in Stage 18's "not doing" list). So they were dropped: `lsblk` is `SIZE LABEL UUID MOUNTPOINT` in device order, and `mount` lists each volume as `LABEL=name on /mnt type vfat` -- `UUID=XXXX-XXXX` when the volume has no label or another one shares it -- the spelling `mount` takes, so a line can be pasted back. The `progs_r19::spell` module holds that rule (host-tested), and Step 1's tests that read names now read the row order. If a later stage adds raw block access, device nodes and names come back with it.

## Step 3 -- `/etc/fstab` and the `HOME` mount
- **Parser (pure, `shell/fstab.rs`, 13 host tests).** `<source> <mount point> <type> <options> [dump [pass]]`; sources are `mounttable::Source`, types `vfat`/`fat`, options only `defaults` (= `auto,fail`), `auto`/`noauto` and `fail`/`nofail`, read left to right (`defaults` is no-op shorthand; the last of a pair wins); **`ro`, `rw`, `noatime` and anything else refuse the line** (nothing else would mean anything here, and read-only is not enforced: mounting read-write what the file calls read-only would surprise); too few or too many fields, a relative mount point, a bad source or type are line-numbered problems, never fatal.
- **`shell::mount_fstab`** runs first in `start_up` (fstab, environment, `$HOME`, profile, prompt), so `/etc/environment`, `$HOME` and the profile may live on a mounted volume (`fs::read_path` already goes through the table). Lines mount in file order through `mounts::mount`, the mount point normalized with `abspath`. Notes on the serial log: parser problems first (`line N: why -- ignored`), then one per line that could not be mounted (`no volume has that label or ID`, `Device or resource busy`, `No such file or directory`, ... `-- skipped`; `nofail` silences only the missing-volume one), then `Fstab: N mount(s) from /etc/fstab.`; a missing file is `Fstab: /etc/fstab: No such file or directory -- nothing to mount.` A `/` line is only checked against the boot-time root (a mismatch is noted and ignored).
- **The image.** `disk/etc/fstab` has the one line `LABEL=HOME /root vfat defaults`; `disk/root` is now created empty by `just disk` (gitignored, like `disk/tmp`); **`.profile` and `utf8-demo.txt` moved (`git mv`) into `disk-home-seed/`**, where `just home-disk` puts them on a new `home.img` (an existing `home.img` made before this Step holds only the README: `just home-reset` to get the rest). No `/etc/profile` was needed; it stays a candidate if the system image should ever carry something every user gets.
- **Tests (+46; 1674 checks).** The harness gets `FSTAB` (text or `None`), an **empty file by default** so no group's own disks are mounted by the image's line, and `files` in an extra-disk description. Groups `fstab` (HOME on `/root` with its own profile run, DATA with options, `noauto`, `nofail`, four kinds of refusal, order before the environment), `fstab_nodisk` (the image's line with no disk: the note, an empty `/root` on the system volume, writable), `fstab_bad` (every kind of bad line, the `/` lines, normalization) and `fstab_missing`.
- **Docs.** `shell.md` ("`/etc/fstab`"), `filesystem.md` (`/root` is a mount point), `tests.md`.

## Step 4a -- `rename` replaces
- **Kernel (`fs/files.rs`).** `rename` resolves the destination's volume and looks it up: same path is a no-op (`0`); a directory into its own subtree is `EINVAL` before anything is removed; a file onto a directory `EISDIR`, a directory onto a file `ENOTDIR`; otherwise an existing destination is deleted (`hadris`' `delete`, which refuses a directory with contents: `ENOTEMPTY`) and the source renamed. `EXDEV` and the mount-point `EBUSY` are as in Step 2 and still come first. Not atomic on FAT: a crash between the delete and the rename costs only the file that was to be replaced, the source being where it was. The user-visible `mv` is unchanged (it still unlinks a plain-file target itself, and moves *into* a directory); Step 4c replaces that.
- **`probe rename OLD NEW`** (test program) calls the syscall with no `mv` rules on top; group **`rename`** (+34 checks; 1708 in all): every case above, the refusals leaving both sides intact, replacing a read-only file, across two volumes (`EXDEV`, destination untouched) and a mount point, `fsck.fat` on the second volume.
- **Docs:** `syscalls.md` (row 38), `filesystem.md`, `tests.md`, `test/README.md`.

## Step 4b -- setting times
- **Syscall 88, `utimensat(path, path_len, times)`.** Linux's number and two-`timespec` array (`UTIME_NOW`/`UTIME_OMIT` in `tv_nsec`, a null array meaning both now); `abi::time` gets the constants, `userlib::{utimens, TimeSet}` the wrapper. Kernel: `fs/fattime.rs` gains the pure `choose` (a `tv_nsec` is one of the two specials or a real fraction, else `EINVAL`) and `checked_fields` (a time FAT cannot hold, before 1980 or after 2107, is `EINVAL` where the existing `fields` clamps); `files::set_times` goes through `hadris`' `FatVolume::set_times` (files and directories, from a path; the volume's root has no entry, `EINVAL`); the access time keeps only its date, odd seconds are dropped, the creation time is not touched. It works on a read-only file, as on Linux.
- **`progs_r19`.** `touch [-c] [-d STRING | -t STAMP | -r FILE] FILE...` (a directory and a read-only file too; wall-clock times in the local zone through the zone database `date` already links, so the binary is 1.3 MB like `date`'s; a gap in daylight saving is `invalid date format`, an ambiguous hour takes the earlier) and `cp -p`. The pure `stamp.rs` (`parse_date`, `parse_stamp`, `fat_to_unix`; 8 host tests) reads the time formats. **The copy engine `copy.rs`** (`Copier`: files and trees, `-n`, `-v`, `-p`) is shared by `cp` now and by `mv` in 4c, and checks each copy's size once closed (a short write from a full disk is an error). `cp -p` keeps the modify time and access date, a file's exec and read-only bits, and each directory's own time (set after its contents are in), also onto another volume.
- **Tests (+87; 1795).** Group `times` (`touch` in every format and both zones, FAT's limits, every refusal, `-r`, directories, `cp -p` for a file, a tree and across volumes against plain `cp`), `probe utimens`/`utimens-null`/`utimens-bad` for the raw syscall (omit, fractions, out-of-range fields, the root, bad pointers); the Stage 18 `tools` group's `touch` expectations changed to today's behavior (a read-only file and a directory can be touched; the new `--help`), and `flags`' `cp --help`.
- **The input flake got worse -- and its window was found.** Once `cp` was the new binary, the deferred `token_queue` "typing during a large copy" flake went from about one run in ten to about one in three (three full suites failed in a row; alone, 6 of 16; the Stage 18 `cp` binary on the same kernel, 1 of 16). The syscalls are the same, so it is timing. The loss is in the device's queue, not ours: the guest's virtio-input event queue has 32 buffers (fixed by `virtio-drivers`), a keystroke is several events, and interrupts are masked during some kernel work, so a long enough stretch fills the buffers and QEMU drops the next events -- before the kernel's own 16-key test queue, which never overflowed (no note in the log). **The stretch is the first half second or so after a program is started** (loading it and the start of the copy): typing the line right after the Enter that starts `cp` lost a key in 4 of 12 runs; 0.15 s later 2 of 12; 0.3 s later 4 of 12; 0.6 s later 0 of 12; 0.8 s or 1 s later 0 of 72. (A first guess, typing more slowly, did not help: an experiment that seemed to show it had slowed the first line too, which moved the window.) So the line is now typed a second after the copy starts (`LAUNCH_SETTLE`), still well inside a copy of about 2.5 s, and the check is strict. This is a real limitation for anyone typing ahead: **keys typed just after starting a program can be dropped**; the real fix -- an owner for the console input queue that drains the device -- stays Stage 26's.
- **Docs.** `syscalls.md` (row 88), `progs.md` (`touch`, `cp`), `tests.md`, `test/README.md`.

## Step 4c -- `mv` between volumes
- **`mv` (`progs_r19`).** On one volume nothing changes (probe the target, `rename`, the kernel replaces a plain-file target itself -- Stage 18's `mv` unlinked it first). On `EXDEV` the source, a file or a whole tree, is copied and then removed: **copy under a hidden name in the destination directory (`.mv-partial`, then `.mv-partial.1`, ... for the first free), checking each file's size; rename it into place; only then remove the source.** A failure in the copy removes the hidden copy and leaves the source whole and an existing destination untouched; a failure while removing the source leaves the destination complete and names the entries left. The copy is `progs_r19::copy` with `preserve` (modify time, access date, exec and read-only bits, each directory's own time), and `remove_tree` (contents before directory, with or without reporting) is new there.
- **Two kernel fixes it turned up.** (1) **`rename` kept nothing of the entry's times:** `hadris` stamps a renamed entry with the clock, so a cross-volume `mv` came out "modified now" and even a same-volume `mv` changed a file's modify time (a wart since Stage 12). `files::rename` now puts the old modify and access times back, as POSIX does (rename group: file and directory). (2) **A full volume was `EIO`:** `write` and close mapped every `hadris` error to `EIO`; they now use `map_fat_err`, so a full disk is `No space left on device` (`ENOSPC`).
- **Tests (+45; 1840).** Group `mv_volumes`: a file each way (time, exec, read-only kept), several sources, replacing (and `-n`, `-v`), a tree each way with every time, a taken hidden name, and three failures on a 128 KiB destination disk -- a file, a file replacing another, a tree -- each leaving the source `cmp`-equal, the existing file untouched and nothing hidden behind; plus what stays refused; `fsck.fat` on both disks. `mounts` no longer asserts `EXDEV` through `mv` (that is `rename`'s and `mv_volumes`').
- **A copy's modify time can be older than its creation time** (`stat` shows both): the creation time is the copy's own, as in a Windows copy; only the modify time and access date are set (`cp -p`, `mv` between volumes, `touch -d`).
- **Docs.** `progs.md` (`mv`, `cp`), `syscalls.md` (`rename` keeps times, `write` gives `ENOSPC`), `tests.md`.

## Step 4d -- `mv`'s options, and no access times
- **`mv -i -u -b -t -T`** in `progs_r19` (the option set was taken from the host's coreutils, including its messages and exit statuses: a declined `-i` is status 1, a skipped `-u` is 0 and silent, `-b` keeps `NAME~` and `-v` says so). `-i` asks on standard error and reads the answer from standard input; the last of `-f`/`-i`/`-n` wins; `-t` values are gathered in the single option pass (the second-walk pitfall again). Group `mv_options` (65 checks). `-S`, `--backup=CONTROL` and `--update=...` are not there.
- **Access times dropped, on the user's decision ("FAT doesn't store a fine enough resolution"):** `utimensat` still takes Linux's two `timespec`s but the **access time is accepted and ignored** (its `tv_nsec` is still validated); `rename` restores only the modify time; `touch` and `cp -p` and `mv` set only the modify time (`touch -r` reads only the reference's modify time); the access date FAT stores is left as the volume wrote it. `touch -a`/`-m` stay out for the same reason. `stat` never showed it.
- **Left as they are, by decision:** `/etc/profile` (a `.profile` can simply be deleted, and would be restricted to what `/etc/profile` does not set if one is ever added), `vda`-style names, read-only mounts (a possible future step), `stat` of a mount point (the FAT epoch: Linux's FAT root shows an arbitrary time too), and the input flake's kernel fix (Stage 26).
